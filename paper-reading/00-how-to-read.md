# 第一次读编译器，先跟一件东西走完

[论文路线目录](README.md) · [下一篇：从论文进入 Triton-C](01-language.md)

第一次阅读的单位是一条**能说清楚的问题**。比如「`float A[2, 3]` 的 2 和 3 最后存在哪里，谁用它？」一个文件可以回答几个不同的问题，一条问题也常常跨几个文件。目录帮助找入口，函数是停下来细读的地方。读完一个函数后，拿它的答案回到刚才的问题。

## 先看入口的一段，再决定进去哪个函数

打开[旧运行时的 function::make](../../triton-legacy/lib/runtime/function.cc#L254)，先滚到 `// pre-process`。这个函数做的事是为一组编译选项准备可调用的设备程序。顶部的缓存分支可以读成「找到可用产物就提前返回」。为了理解**第一次生成**的路线，先走继续往下的分支。按源码上实际出现的四步读：

| 看到的代码 | 这一行过后手上有什么 | 要继续追的情况 |
|---|---|---|
| `cpp.Process(tokens)` | 源码被拆成 token，配置里的宏已经交给预处理器。例如编译选项可以让 `TM` 变成具体数字 | 如果不清楚 shape 的数字什么时候确定，就在这里看宏的输入；了解数字从配置来就可以返回 |
| `parser.Parse()` | parser 根据 token 建立语法树。树上有声明、表达式等节点 | 想知道 `[2, 3]` 怎么识别，去 parser 查这一条声明；例如 [`float a[2,3]` 怎样创建 TileType](01-language.md#read-parser-expressions)，讲义会逐行跟到生成的节点 |
| `auto ir = make_ir(parser)` | 从语法树得到一个 IR 模块，`ir` 指向编译器接下来要处理的程序 | 想知道形状怎样进入 IR，从这里进 [`make_ir`](../../triton-legacy/lib/runtime/function.cc#L191)，沿 `gen.Gen(module)` 找声明和类型的处理 |
| `bin = make_bin(*ir, ...)` | 编译流程读取并处理模块，交回设备代码所在的驱动模块 | 想知道刚才的 shape 怎样影响优化，进 `make_bin` 找一个读 shape 的 pass |

把表中最容易卡住的两行连着读。`auto ir = make_ir(parser)` 在右边调用函数，左边创建名字 `ir` 接住它的结果。`auto` 让 C++ 从右边推断类型，此处 `make_ir` 返回 `std::unique_ptr<ir::module>`，也就是负责管理一个 IR module 的指针。下一行 `make_bin(*ir, ...)` 里的 `*ir` 取出指针所指的模块，因为 `make_bin` 的第一个形参是 `ir::module &module`，它需要通过引用访问这个模块。ASCII 字符 `*` 写在类型右边如 `type*` 时表示「指针类型」，写在已有变量左边如 `*ir` 时表示「取得所指对象」。[看 make_ir 与 make_bin 相邻的定义](../../triton-legacy/lib/runtime/function.cc#L191)你可以把本轮记录写成一行：`源文字 → token → 语法树 → 带类型的 IR → 设备代码`。往后每读到一个对象，先问自己它落在哪个箭头的哪一端。

## 看到 include、import、调用和类型，分别怎么处理

- **读到 `#include` 或 `import`。** 它告诉你某个名字从哪里可用。先读当前正在追的语句。比如 `type.h` 包含 `<vector>`，此处知道 vector 是有顺序、长度可变的一组值，就能读 `shape=[2,3]` 的含义；要解决特殊的容器行为时才查标准库。Python 中也一样，先找到当前使用的名字，例如 `triton.ops.einsum(...)`，再追该名字的实际定义。
- **读到函数调用。** 先把实参和返回值写下来。若只需知道 `get_tile_shapes()` 交回 `[2,3]`，读到返回字段即可。如果困惑的是「谁填了这个字段」，就转去找构造函数或对该字段赋值的地方。只读能改变你当前判断的分支。
- **读到类、父类或成员。** 先确认这一处关系怎么用。例如 `instruction : public user`、`user : public value` 意味着一条指令可以记录操作数，还能带一个类型。需要确认类型放在哪里，就跟到 `value::ty_`。目录里的其他子类等遇到时再回来读。
- **读到同名函数或接口。** 先看调用的对象和所在模块。例如 `Generator::GenIRType` 的输入是前端的 `::Type*`，结果是 `ir::type*`。这两个名字长得像，却位于不同层。若方法由实际类型决定，就查对象在哪里创建，再找对应实现。
- **读完下层函数。** 回到调用处，用一句话在原来的位置替换这次跳转，例如「`get_same_shapes` 取原 tile 的尺寸，搭配新的元素类型」。接着读调用后的第一位消费者。这样能把几层跳转重新连回原来的程序。

## 怎么判断这一段读够了

用两个方向交叉验证：找**一位创建者**和**一位消费者**。以 tile 类型为例，前端从声明建立 IR 类型，load 用地址 tile 的形状建立结果 tile 类型。能用 `[2,3]` 写出输入和输出，能指出中间是哪个字段保存它，就已经回答了当前问题。缓存表的内部实现、所有标量类型、所有 load 后端属于可以日后单独带着问题回来的路径。

第一次读完整系统，可以只保留下面这几条接力点。每次进一个新文件，先读表中提到的几行，再用右列判断是否能返回。

| 想读懂的接力 | 进入哪一站 | 返回前说清一句话 |
|---|---|---|
| 源码声明到带类型的值 | [从 type.h 跟一块 tile](02-ir.md#read-tile-type) | 元素类型和 shape 分别在哪里，哪个操作会读它们？ |
| 源码里的条件 load 到 IR | [从 parser 跟到 builder](02-ir.md#mask-to-builder) | 三个输入是什么，指令怎样得到结果类型？ |
| IR 进入改写和同步 | [从 make_bin 选一个 pass](03-compiler.md#read-one-pass) | 它读哪些对象、改了什么、执行后谁继续用？ |
